## 1. Manifest V3 in Safari 26 (VERIFIED unless marked)

- MV2 and MV3 both supported since Safari 15.4; "With manifest version 3, all background pages are nonpersistent." — https://developer.apple.com/documentation/safariservices/assessing-your-safari-web-extension-s-browser-compatibility
- Background: "In iOS, you must make your background page nonpersistent." Either `"background": {"scripts": [...], "persistent": false}` or `"background": {"service_worker": "background.js"}`; Apple: "Use a service worker for better compatibility with other browsers." When nonpersistent: register listeners at top level, persist state with Storage API, use Alarms not setTimeout. macOS exception: keep persistent only if you use `webRequest`. — https://developer.apple.com/documentation/safariservices/optimizing-your-web-extension-for-safari
  - MDN BCD: `background.service_worker` Safari 15.4+, iOS mirror; `background.scripts` works in MV2 *or* MV3 on Safari; Chrome `background.scripts` is MV2-only; Firefox `service_worker` = false. — https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/manifest/background.json
  - PRACTICAL (developer reports, Apple partially acknowledged): on physical iPhones the MV3 **service worker gets permanently killed ~30–45 s after install** and never wakes (iOS 17.4→18.6.2 reports; thread does not cover iOS 26). Apple said fixed in 17.6.1; devs say not. Widely used workaround = `"background": {"scripts": ["background.js"], "persistent": false}` (also what the Safari 26 dev-mode blog recommends for debuggability). — https://developer.apple.com/forums/thread/758346 , https://www.stefanvd.net/blog/?p=2105 . Status on iOS 26.x: UNVERIFIED → ship the `scripts + persistent:false` form; it is valid MV3 in Safari (and in Firefox), only Chrome needs `service_worker` (see §6).
- declarativeNetRequest: supported since Safari 15 (iOS mirror). Actions: block, allow, upgradeScheme, allowAllRequests (main_frame only), redirect (15.4+), modifyHeaders (16.4+, needs `declarativeNetRequestWithHostAccess` + host permission). Rule APIs: getEnabledRulesets, updateEnabledRulesets, MAX_NUMBER_OF_STATIC_RULESETS, updateDynamicRules/getDynamicRules (15.4+), updateSessionRules/getSessionRules, getMatchedRules, setExtensionActionOptions (16.4+). ResourceTypes: main_frame, sub_frame, stylesheet, script, image, font, xmlhttprequest, ping, media, websocket, other. Conditions: domainType, excludedResourceTypes, isUrlFilterCaseSensitive, regexFilter, resourceTypes. — https://developer.apple.com/documentation/safariservices/blocking-content-with-your-safari-web-extension ; BCD: MAX_NUMBER_OF_DYNAMIC_RULES / GUARANTEED_MINIMUM_STATIC_RULES / MAX_NUMBER_OF_SESSION_RULES constants = not exposed in Safari; MAX_NUMBER_OF_ENABLED_STATIC_RULESETS 16.4+. — https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/api/declarativeNetRequest.json . Numeric rule caps: UNVERIFIED (WWDC22 notes cited "50 rulesets, 10 enabled"; not fetched). Safari 26.0 fixed DNR priority ordering, allowAllRequests vs block, redirects to extension resources. — https://developer.apple.com/documentation/safari-release-notes/safari-26-release-notes
  - For THIS product DNR is of limited use: feed items are not separate requests you can block; the filtering is DOM-level. DNR is useful only for blocking known slop CDNs/trackers.
- `webRequest`: "Not supported in iOS"; blocking never supported anywhere in Safari (`webRequestBlocking` unsupported). — assessing… doc above.
- scripting API: 15.4+; `executeScript` `world: "MAIN"` 15.4+ (BCD) ; `registerContentScripts` 16.4+ (Apple staff: "Safari 16.4 does support 'MAIN' for registerContentScripts" — https://developer.apple.com/forums/thread/728849); `injectImmediately` not supported (scripts always injected immediately); `insertCSS/removeCSS` lack `origin`, `allFrames`, `frameIds`. Safari 26.0 fixed `excludeMatches` being ignored and a registerContentScripts "Failed to add content script" error. — BCD scripting.json + Safari 26 release notes.
- content_scripts: `run_at` supported (Safari 14 / iOS 15) — but "Content scripts are not applied to tabs until the user grants permission via the extension's access alert"; `document_start` honored on loads after permission. `world` key in the manifest: BCD says Safari 18 (iOS mirror) — https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/manifest/content_scripts.json — yet Xcode 26.6's converter warns `world` unsupported (reproduced above). CONFLICT → treat manifest `world` as UNVERIFIED; default world is ISOLATED anyway (that is what you want for a feed filter), and if you ever need MAIN use `scripting.registerContentScripts({world:"MAIN"})` or `executeScript`. `match_about_blank`, `match_origin_as_fallback`: Safari 18.4.
- storage: `storage.local` limit 5 MB; `"unlimitedStorage"` → unlimited in Safari 16+; `storage.session` 16.4+; **`storage.sync`: "Storage mechanism implemented, but syncing not supported"** (it is just local). — assessing… doc. So cross-device sync of your allow/deny lists must go through your own app (App Group + CloudKit/iCloud KVS in the containing app) — not via storage.sync. Note Safari 17+ profiles: `SFExtensionProfileKey` in native messages lets you partition per profile.
- Namespaces/async: both `chrome.*` and `browser.*`; both callbacks and Promises. — assessing… doc.
- MutationObserver performance: no Apple-published guidance found (UNVERIFIED/none). Engineering note only: observe the narrowest feed container (not `document.body` with subtree on `document_start` forever), batch work in `requestIdleCallback`/rAF, hide via a CSS class injected at `document_start` (`css` in content_scripts, run_at document_start) and let JS un-hide, so first paint never shows slop. Jeff Johnson measured mobile Safari web pages crashing at ~100 MB (iPhone SE 3) / ~200 MB (iPad 8) on iOS 26.2 and a 64 MB cap on `runtime.sendMessage` payloads (iOS and Mac) — https://lapcatsoftware.com/articles/2026/1/7.html (secondary, measured not documented).
- Other Safari 26.x extension changes: 26.0 — menubar commands (macOS/iPadOS), extensions in SafariDriver, `dom.openOrClosedShadowRoot()` — https://webkit.org/blog/17333/webkit-features-in-safari-26-0/ ; 26.2 (Dec 2025) — `SFSafariExtensionState.isEnabled` now on iOS/iPadOS/visionOS, `SFSafariSettings.openExtensionsSettings(forIdentifiers:)` deep link into Safari Extension Settings, `browser.runtime.getVersion()`; app-extension→web-extension permission migration on macOS — https://webkit.org/blog/17640/webkit-features-for-safari-26-2/ ; 26.4 — `window.open` fix; 26.5 — trailing-comma manifest fix. — https://developer.apple.com/documentation/safari-release-notes/safari-26_4-release-notes , …/safari-26_5-release-notes . Safari 27 (WWDC26): no new extension APIs announced beyond packaging without Xcode — https://webkit.org/blog/17974/web-technology-sessions-at-wwdc26/ .

## 2. Native messaging on iOS (VERIFIED)

- Source: https://developer.apple.com/documentation/safariservices/messaging-between-the-app-and-javascript-in-a-safari-web-extension
- "Content scripts that are injected into web content cannot send messages to the native app extension." Only the background script or extension UI pages may call `browser.runtime.sendNativeMessage("application.id", msg, cb)`; Safari ignores the id and routes to the containing app's own appex. Needs `"nativeMessaging"` permission. So the pipeline is: content script → `browser.runtime.sendMessage` → background → `sendNativeMessage` → `SafariWebExtensionHandler.beginRequest(with:)` (NSExtensionRequestHandling) → reply via `NSExtensionItem.userInfo[SFExtensionMessageKey]` + `context.completeRequest(returningItems:)`.
- iOS asymmetry: "You can't send messages from a containing iOS app to your web extension's JavaScript scripts." (`connectNative` port + `SFSafariApplication.dispatchMessage` is macOS-only.) App ↔ extension state sharing on iOS = App Group container / shared UserDefaults, read by the handler on each request.
- The handler runs in the appex process, NOT in your app. Payload size limit: UNVERIFIED (none documented; the 64 MB figure above is for `runtime.sendMessage`). Latency: UNVERIFIED (no numbers published; it is an XPC round trip per call — batch items).
- Memory for the appex (where Core ML would run): Apple engineer on forums: 6 MB in iOS 15.0 betas, "the limit increased to 80MB in the latest iOS 15.1 beta" — https://developer.apple.com/forums/thread/687642 . No newer official figure (UNVERIFIED for iOS 26). Design implication: a small on-device classifier (few-MB quantized Core ML / NL model, or Natural Language framework) is feasible in the handler; a large vision/LLM is not — do heavy inference in the main app (App Group queue, Background Tasks) or call a server, and keep the handler stateless and short-lived (it is spun up per request).
- Error 4099 / "Couldn't communicate with a helper application" appears when the appex isn't installed/signed — https://developer.apple.com/forums/thread/747067 (anecdotal).

## 3. Home-Screen web apps on iOS (mostly VERIFIED negative)

- iOS 26: "Added support for any website to become a web app on iOS or iPadOS" (Safari 26 release notes); every Add-to-Home-Screen site opens as a web app by default, toggle "Open as Web App". — https://webkit.org/blog/17333/webkit-features-in-safari-26-0/
- Extensions in web apps: Apple: "Safari web extensions are available in Mac web apps in macOS 15 and later." — https://developer.apple.com/documentation/safariservices/safari-web-extensions . Nothing equivalent for iOS. Jeff Johnson (Sep 2024): "this new feature does not apply to home screen apps on iOS 18. It's Mac-only." — https://underpassapp.com/news/2024/9/5.html . WebKit bug 238151 ("Safari Web Extensions and Content Blockers not working when a standalone website is added to the home screen", iOS 15) was closed MOVED: "Both of these are issues within Safari and not within WebKit." — https://bugs.webkit.org/show_bug.cgi?id=238151 . Apple forum question on this (Feb 2023) has zero replies — https://developer.apple.com/forums/thread/725178 . No iOS 26 release note changes this. Conclusion: **assume content scripts do NOT run in iOS Home-Screen web apps** (iOS 26 status itself UNVERIFIED by a primary source, but no evidence of support).
- Ways to make instagram.com "feel like an app" with filtering active on iPhone: (a) the user opens instagram.com in Safari proper (bookmark/tab) — extension works; (b) your own app hosts a `WKWebView` pointed at instagram.com and injects `WKUserScript`s — see §4; (c) `SFSafariViewController` does NOT run your extension content scripts (UNVERIFIED — not documented either way; content blockers do apply to SFSafariViewController but web extensions are Safari-app features).

## 4. WKWebView wrapper + App Review (VERIFIED guideline text; precedent partly secondary)

- Technically: WKWebView supports `WKUserScript` at `.atDocumentStart/.atDocumentEnd`, `forMainFrameOnly`, and `WKContentWorld` (isolated worlds), plus `WKContentRuleList`. Nothing stops injecting into instagram.com/x.com/youtube.com (Instagram's own in-app browser is itself a WKWebView). Login inside a WKWebView: UNVERIFIED for 2026 (no source says Meta/X block it; Google blocks OAuth in embedded webviews, which affects YouTube sign-in via Google — treat as risk; use `WKWebsiteDataStore` persistent store).
- Guidelines (https://developer.apple.com/app-store/review/guidelines/):
  - 2.5.6 "Apps that browse the web must use the appropriate WebKit framework and WebKit JavaScript." (alt engines only via EU/Japan entitlement).
  - 4.2 "Your app should include features, content, and UI that elevate it beyond a repackaged website… If your app is not particularly useful, unique, or 'app-like,' it doesn't belong on the App Store." 4.2.2 "apps shouldn't primarily be marketing materials, advertisements, web clippings, content aggregators, or a collection of links."
  - 5.2.2 "If your app uses, accesses, monetizes access to, or displays content from a third-party service, ensure that you are specifically permitted to do so under the service's terms of use. Authorization must be provided upon request."
  - 5.2.3 (media download) only matters if you add save/download.
- Precedent: **Juno for YouTube** (visionOS) — "Juno is just a web view, and acts as little more than a browser extension" that "modifies CSS…", "doesn't block ads in any capacity"; removed 2024-10-01 after YouTube told Apple it "modifies the website in a way they don't approve of" — https://christianselig.com/2024/10/juno-removed/ . YouTube ToS forbids to "alter, modify or otherwise use any part of the Service" and to "circumvent, disable, fraudulently engage with, or otherwise interfere with any part of the Service" — https://www.youtube.com/t/terms . So a wrapper that modifies youtube.com/instagram.com/x.com is exposed to a 5.2.2 takedown on a rightsholder complaint even if it passes initial review; generic "WebView of a site" apps are routinely rejected under 4.2 (many forum reports, e.g. https://developer.apple.com/forums/thread/108931 — secondary).
- Counter-precedent: **Safari extensions that rewrite youtube.com** ship on the App Store for years — Vinegar / Baking Soda (Zhenyi Tan, $1.99, replaces YouTube's player, removes ads) — https://9to5mac.com/2021/12/04/safari-native-youtube-app-player/ , https://applevis.com/apps/ios/safari-extensions/vinegar-tube-cleaner (secondary). Orion (Kagi) ships an iOS browser running Chrome/Firefox extensions under WebKit — https://kagi.com/orion/ (vendor claim). "Dolphin": nothing relevant found (UNVERIFIED).
- Decision: the **Safari Web Extension is the App-Review-safe primary product**; a WKWebView "feed mode" inside your app is a second-tier feature to position as a *reader/filter tool the user configures* (real native UI: rules, stats, model settings) not as "Instagram app" — never use the sites' names/logos in the app name/icon.

## 6. Same folder as a Chrome extension (VERIFIED)

- Chrome ignores unknown keys; `browser_specific_settings` only yields a harmless "Unrecognized manifest key" warning (Chromium lists it as an ignored key) — https://chromium.googlesource.com/chromium/src/+/main/extensions/common/manifest_constants.h (secondary confirmation via forum reports).
- Real blockers: Chrome MV3 requires `background.service_worker`; `background.scripts` is MV2-only in Chrome (BCD). Safari/Firefox accept `scripts + persistent:false` in MV3. → keep one source tree and emit two manifests (or one manifest with `service_worker` and accept the iOS kill risk in §1). Chrome ≥148 exposes `browser.*` natively; before that use `globalThis.browser ??= chrome` — https://developer.chrome.com/docs/extensions/develop/concepts/browser-namespace . Chrome also needs icons (converter warned "manifest.json is missing icons").
- Safari-only keys/behaviours to avoid relying on: `update_url` ignored ("Handle Safari web extension updates with the App Store"), `webRequestBlocking`, `storage.sync` not synced, `identity` unsupported, `contextMenus` unsupported on iOS, `windows.create/remove/update` unsupported on iOS, `tabs.executeScript` lacks `runAt`.

## 7. 2026 distribution / dev-mode rules (VERIFIED)

- iOS: extension ships ONLY inside a signed iOS app. "You can test your unsigned visionOS or iOS web extension in the simulators during development. For testing on device, beta testing with other users, and distributing to users in the App Store, you need to sign your extension and containing visionOS or iOS app." "You must be a member of the Apple Developer Program to test on a device." Beta: ad-hoc signed IPA or TestFlight. — https://developer.apple.com/documentation/safariservices/distributing-your-safari-web-extension , https://developer.apple.com/documentation/safariservices/running-your-safari-web-extension . No "temporary/unsigned extension" mode exists on iOS (nothing found; iOS 26.x release notes silent). Enable on device: Safari ▸ More ▸ Extensions, or Settings ▸ Apps ▸ Safari ▸ Extensions.
- iOS 26.0 bug: freshly built extensions showed "<Ext> is no longer available" on physical devices (sim OK), log "The provided identifier … is invalid"; Apple closed reports as duplicates of an open bug; fixed in iOS 26.1 beta 2 per developers — https://developer.apple.com/forums/thread/799935 , https://developer.apple.com/forums/thread/790859 . → run the iPhone on ≥ 26.1 (and if "no longer available" appears, check cert expiry / re-run).
- iOS 26 silent-popup case: converter run against a repo root produced an appex containing only manifest.json; stage the extension folder cleanly (or use `--copy-resources` from a clean dir) and `unzip -l` the IPA to confirm resources — https://developer.apple.com/forums/thread/825155 .
- macOS: Safari 17+ → Settings ▸ Advanced ▸ "Show features for web developers", then Settings ▸ Developer ▸ "Allow unsigned extensions" (resets on every Safari quit; same per Mac web app). Safari 26 adds **Settings ▸ Developer ▸ "Add Temporary Extension…"** to load a bare folder/zip without Xcode; "Safari removes temporary extensions after 24 hours or when you quit Safari." — running… doc; https://www.stefanvd.net/blog/?p=2105 . Outside the App Store on macOS: Developer ID + notarization is allowed.
- Web-based **Safari Web Extension Packager** in App Store Connect (Users and Access ▸ Xcode Cloud ▸ Safari Web Extension Packager): upload the extension zip, get a signed iOS+macOS app, TestFlight it, submit — "without requiring a Mac or access to Xcode"; compute billed against the 25 h/month Xcode Cloud allowance; requires Developer Program. — https://developer.apple.com/documentation/safariservices/packaging-and-distributing-safari-web-extensions-with-app-store-connect . Limitation for this product: the packaged app has NO custom native code (no Core ML handler, no App Group UI) → use Xcode/XcodeGen path since you want a real companion app.
- Code-signing on this Mac: converter leaves no entitlements; macOS Safari extensions must be App-Sandboxed (converter sets ENABLE_APP_SANDBOX=YES on the macOS extension). App Groups must be added by hand if the app and handler share data.

## 8. Recommended architecture given the above

1. One repo, one `extension/` folder (MV3, `background.scripts + persistent:false`, content scripts per site at `document_start` with a CSS pre-hide, `storage.local` for rules, `nativeMessaging`), two manifest variants (Safari, Chrome).
2. XcodeGen `project.yml` (spec in §5) → iOS app + iOS appex + macOS app + macOS appex sharing the folder; App Group for settings + CloudKit/NSUbiquitousKeyValueStore sync in the apps (storage.sync is dead on Safari).
3. Classification: tier 1 heuristics in JS (hashtags, "AI-generated" labels, account lists, caption patterns); tier 2 `sendNativeMessage` → handler running a small Core ML/NaturalLanguage model (stay well under ~80 MB, batch items per call); tier 3 optional server.
4. Mac: dogfood instantly via Settings ▸ Developer ▸ Add Temporary Extension (no signing). iPhone: must build-and-run from Xcode with a Developer Program team on a ≥ iOS 26.1 device — first install the iOS platform in Xcode 26.6.
5. Do NOT build the product as a WKWebView wrapper of the three sites; keep an optional in-app "filtered feed" WKWebView behind real native UI and expect 5.2.2 exposure to platform complaints (Juno precedent).
